# ADR-003 — Ansai Core Extraction from EduManage
Date: May 2026
Status: Active
Decided by: Amasai Melchizedek

---

## Decision

The shared infrastructure currently embedded inside
the EduManage codebase is extracted into a separate
ansai-core repository as @ansai/ scoped packages.

EduManage then imports from ansai-core rather than
containing these primitives inline.

Extraction sequence:
1. @ansai/tenancy — tenant isolation engine
2. @ansai/auth — authentication and session management
3. @ansai/roles — role-based access control
4. @ansai/events — event emission and subscription
5. @ansai/audit — audit logging
6. @ansai/pipeline — data tributary skeleton

---

## Reason

**The problem this solves:**

EduManage is the first Ansai product line.
When the agriculture product, the health product,
and the logistics product are built — they will all
need the same authentication, tenancy, roles, events,
and audit logging that EduManage already has.

Without extraction, three things happen:
The same logic gets written three times.
Security fixes must be applied in three places.
Improvements compound inside one product and
never benefit the others.

With extraction:
The logic is written once.
Security fixes propagate to every product simultaneously.
Improvements compound across the entire ecosystem.

**Why now, before the first paying school:**

Extracting from a live system with paying schools
carries operational risk. A migration error during
term time when schools are actively collecting fees
is a mission-critical failure.

Extracting before commercial onboarding means
the risk is contained to the soft pilot schools —
who understand they are testing a pre-commercial product
and have no contractual SLA obligations.

The two to three day cost of extraction now prevents
months of technical debt accumulation that would
make future extraction significantly more dangerous.

**Why not rewrite:**

The existing EduManage authentication, tenancy, and
role logic is production-ready and battle-tested
through development. It works. The extraction is
surgical movement — not a rewrite.

Logic does not change.
Behavior does not change.
Import paths change.
Tests run continuously throughout to verify this.

---

## Consequences

**What this means for EduManage:**

EduManage becomes a consumer of Ansai Core primitives.
The import paths change. The behavior is identical.
Every @ansai/ import is a package maintained in ansai-core.
EduManage engineers do not modify @ansai/ packages —
they raise issues or propose changes through
the Category 2 amendment process.

**What this means for the extraction sprint:**

The sprint runs over two to three focused days.
Tests run continuously throughout — not after.
Each package is extracted and verified independently
before moving to the next.
No package is considered extracted until EduManage
imports it successfully and all tests pass.

If any test fails during extraction:
Stop the sprint. Diagnose the failure.
Do not continue to the next package with failing tests.
The tests are the verification environment.

**What this means for future product lines:**

Every future Ansai product line starts by importing
@ansai/ packages. They inherit the security baseline,
the tenancy model, the role architecture, and the
audit trail without writing a line of infrastructure.

The extraction cost is paid once.
The benefit is permanent.

**Rollback plan:**

If the extraction sprint produces critical failures:
Revert EduManage to import from its own inline code.
Document what failed in HEALTH.md.
Redesign the extraction approach.
The original EduManage codebase is not deleted during
extraction — it is the fallback until all tests pass.
