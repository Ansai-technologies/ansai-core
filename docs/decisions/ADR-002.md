# ADR-002 — Authentication Architecture
Date: May 2026
Status: Active
Decided by: Amasai Melchizedek

---

## Decision

EduManage and all Ansai product lines use JWT-based
authentication with refresh token rotation.

Access tokens: short-lived, 15 minutes.
Refresh tokens: long-lived, 7 days, httpOnly cookie.
Password hashing: bcrypt, minimum 12 rounds.
Account lockout: 5 consecutive failures, manual unlock.
Rate limiting: 10 requests per minute on login endpoints.

Implemented in @ansai/auth. No product line implements
its own authentication. All authentication goes through
the primitive.

---

## Reason

**Why JWT with refresh token rotation:**

Short-lived access tokens limit the damage window
if a token is compromised. A stolen access token
is valid for at most 15 minutes.

Refresh token rotation means every refresh invalidates
the previous refresh token and issues a new one.
A stolen refresh token can only be used once —
the legitimate user's next refresh will detect the
mismatch and invalidate the entire session.

httpOnly cookies for refresh tokens prevent JavaScript
access — XSS attacks cannot steal the refresh token.

This combination provides strong security without
requiring the institution to manage complex session
infrastructure.

**Why not session-based authentication:**

Session storage on the server creates statefulness
that complicates horizontal scaling.
JWT is stateless — any server can validate any token
without shared session storage.
At Ansai's current scale this is not a critical concern
but the decision remains correct for the long term.

**Why not single long-lived tokens:**

A 24-hour token on a product handling financial records
and student data is not acceptable.
If a token is compromised — through XSS, through a
shared device, through a screenshot — the attacker
has 24 hours of access. 15 minutes is the correct
window for this category of institutional data.

**Why bcrypt at 12 rounds:**

bcrypt is deliberately slow. 12 rounds provides
adequate protection against brute force attacks
on stolen password hashes while remaining
fast enough for legitimate login flows.
MD5, SHA-1, and unsalted hashes are explicitly
prohibited — they provide no meaningful protection
against modern GPU-based attacks.

---

## Consequences

**What this means for all engineers and agents:**

Never implement custom authentication in any product line.
@ansai/auth is the only authentication implementation.

Never store tokens in localStorage.
Refresh tokens go in httpOnly cookies only.

Never extend access token lifetime beyond 15 minutes
regardless of user experience pressure.
If users complain about being logged out —
fix the refresh token rotation, not the token lifetime.

Never reduce bcrypt rounds below 12.
If login feels slow — investigate the hash comparison
implementation, not the round count.

**What this means for new product lines:**

Every new Ansai product line inherits @ansai/auth
without modification. Authentication is solved once.
Any product-specific authentication requirement
is implemented as a configuration of @ansai/auth —
never as a parallel implementation.

**What this means for security testing:**

Authentication is a critical path.
Login, lockout, and token validation tests must pass
before any product line accepts real institutional users.
These tests run on every deployment through CI/CD.
