## 01 — The data architecture standard

**Local-first · Sync-always · Backup-automated · Loss-never**

Every Ansai product line that handles institutional data
must implement this data architecture. No exceptions.
This is not a recommendation — it is the minimum standard
for any product that calls itself operational infrastructure.

| Principle | Meaning |
|-----------|---------|
| Local-first | Data is written to the device first — immediately, without waiting for a network response. The sync to the server happens in the background. |
| Sync-always | Continuous background sync when connectivity exists. Maximum 30-second gap for critical data — financial records, attendance. Exponential backoff on failure. |
| Backup-automated | Server replicates to backup automatically. Three layers minimum: local write → server sync → off-site backup. No manual backup processes. |
| Loss-never | A user who enters data on a device with no internet connection must never lose that data. It is written locally and synced when connectivity returns. |

### Implementation standard

Service Workers (Workbox) for background sync and caching.
IndexedDB for local structured storage.
CRDTs for conflict-free merge logic when a device reconnects
after an offline period.

These are the required tools.
Equivalent alternatives require documented justification
and founder approval — recorded as an ADR in
ansai-core/docs/decisions/.

### Why this standard exists

Data architecture is also the foundation of Ansai's
long-term intelligence layer.
Every data point written locally and synced to the server,
structured consistently across product lines, compounds
into institutional intelligence that no competitor
can replicate.

The local-first architecture is not a constraint imposed
by African connectivity conditions.
It is Ansai's compounding advantage.

## 02 — The AI adoption standard

Every engineer on an Ansai product line must operate
at Level 5 minimum on the AI adoption scale.
Level 6 is the target hire profile.

The scale is observable and testable — ask any candidate
to describe how they built something recently.
The answer tells you their level.

| Level | Description | Ansai status |
|-------|-------------|--------------|
| L1 | Writes code by hand. Uses tab completion occasionally. | Not an Ansai hire |
| L2 | IDE agent, supervised. Reviews and approves every agent action. | Not at standard |
| L3 | IDE agent, YOLO mode. Permission gates off. Agent runs automatically. | Approaching standard |
| L4 | Wide agent, diff mode. Engineer reviews diffs, not code. | At minimum |
| L5 | CLI single agent. Runs Claude Code from terminal. Reviews output, not generation. | Minimum Ansai standard |
| L6 | CLI multi-agent 3–5 parallel. One engineer produces what 5 produced in 2022. | Target hire profile |
| L7 | 10+ agents hand-managed. | Senior engineering leadership |
| L8 | Builds own orchestrator. | Founding CTO profile |

### The verification test

In any interview, ask: walk me through the last significant
thing you built and how you built it.

If the answer does not involve AI agents doing the heavy
lifting while the engineer directed and verified —
they are below Level 4.

If they describe running multiple parallel agents
from the terminal — Level 6. Hire accordingly.

### Agentic engineering — the professional standard

Vibe coding raises the floor.
Agentic engineering raises the ceiling.

Vibe coding lets anyone build software by describing
what they want. That is valuable and Ansai respects it.

Agentic engineering is different.
It is the professional discipline of coordinating
fallible agents while preserving correctness, security,
taste, and maintainability.

The agentic engineer does not blindly accept generated code.
They design specs, supervise plans, inspect diffs,
write tests, create evaluation loops, manage permissions,
and preserve quality.

The human remains responsible for everything the agent
produces. Always. Without exception.

You can outsource your thinking.
You cannot outsource your understanding.

## 03 — Quality non-negotiables

### Tests before features

No feature ships to production without tests covering
its critical path.

AI-generated code accumulates technical debt faster
than human-written code and must be tested more
rigorously, not less.
The faster we ship with AI assistance, the more robust
the test suite must be.

### Critical path test coverage — minimum

These four paths must have complete test coverage before
any institution handles real data.
No exceptions. No deferrals.

| Critical path | Standard |
|---------------|----------|
| Financial data | Fee payments, balance calculations, duplicate prevention. 100% critical path coverage before any institution handles real money. |
| Authentication | Login, account lockout, token validation. Security tests must pass before any production deployment. |
| Tenant isolation | Cross-tenant data access prevention. The foundational security guarantee of any multi-tenant Ansai product line. Every query scoped to institutional ID enforced at middleware level — not just application level. |
| Data sync | Offline write, reconnect sync, conflict resolution. The local-first architecture must be verified under real connectivity conditions. |

### Test-driven development standard

Write the test that describes what success looks like
before writing the implementation.

The test fails first. That is the specification.
Then write code until it passes.

This is not optional for critical path features.
The failing test is the verification environment —
it is what makes agent output trustworthy.

### Code review standard

The first pull request from every new engineer is reviewed
in extreme detail by the technical lead.
This is the standard-setting moment.
After that, code review is continuous but the initial
review sets the bar that all subsequent work is held to.

### CI/CD requirement

No code reaches production without passing automated tests.
Auto-deploy on push with no quality gate is not acceptable
for any Ansai product line handling real institutional data.
GitHub Actions or equivalent must gate every deployment.

## 04 — Security baseline

Every Ansai product line must meet these security standards
before any institutional user is onboarded.
These are enforced at the code level — middleware,
database constraints, validation layers.
They are not guidelines. They are structural requirements.

| Standard | Requirement |
|----------|-------------|
| Authentication | JWT with refresh token rotation. Short-lived access tokens — 15 minutes. Long-lived refresh tokens — 7 days, httpOnly cookie. No 24-hour single-token windows on products handling financial or personal data. |
| Password hashing | bcrypt minimum 12 rounds. No MD5, SHA-1, or unsalted hashes anywhere in the codebase. |
| Rate limiting | Login endpoints: 10 requests per minute. Public-facing endpoints: configurable per endpoint risk level. |
| Account lockout | 5 consecutive failed login attempts triggers lockout. Counter resets on successful login. |
| Tenant isolation | Every query scoped to institutional ID enforced at middleware level — not just application level. This is the foundational security guarantee. No exceptions. |
| Audit logging | Every data mutation — CREATE, UPDATE, DELETE — recorded with user ID, timestamp, IP address, and JSON diff. Best-effort — failures do not block operations. |
| File uploads | MIME type validation. Size limits enforced server-side. UUID-based storage keys to prevent enumeration. No user-controlled file paths. |
| Dependencies | Regular security patching. No known critical CVEs in production dependencies. Automated dependency scanning in CI pipeline. |

### The three-layer security model

Security in Ansai products is enforced in three layers
simultaneously. All three must be present.

**Layer 1 — Code enforces.**
Middleware, constraints, validation.
The system physically prevents the violation regardless
of what any agent or human does.

**Layer 2 — Agent recognizes.**
The AGENTS.md constitution makes serious violations
explicitly named and unambiguous.
The agent knows what a gross violation looks like
and can refuse, flag, or escalate — rather than
proceeding blindly.

**Layer 3 — Human reviews.**
Anything touching the data pipeline, the tenancy engine,
financial records, or authentication requires explicit
human approval before merge.
No agent merges these autonomously.

## 05 — The infrastructure-aware engineering standard

Every Ansai product line is designed for the connectivity
conditions that African institutions actually experience —
not the conditions assumed in a developed-market office.

This is not a constraint to work around.
It is the engineering philosophy that gives Ansai
structural advantage over every competitor that builds
for fibre-first assumptions.

**2G-first.**
Every feature is designed for 2G connectivity first.
Fibre is the upgrade path, not the assumption.

**Bundle sizes are minimised.**
Every kilobyte costs real money for users on mobile data.

**Images are compressed, lazy-loaded, and cached aggressively.**
Photos of students and staff should not require
a fast connection to display.

**API responses are paginated and minimal.**
No endpoint returns more data than the UI needs.
Over-fetching is a performance violation.

**Failure states are designed.**
Every screen that loads data must handle the case
where that data does not arrive.
Spinners that time out silently are unacceptable.

**Offline is the baseline.**
The local-first architecture is not a fallback mode.
It is the primary mode.
Online sync is the enhancement.

## 06 — The deep module standard

Every Ansai module is designed as a deep module —
a large amount of functionality behind a simple interface.

Shallow modules — limited functionality with complex
interfaces — are a design failure.
They expose complexity without absorbing it.
They make the codebase harder for both humans and
agents to navigate, test, and understand.

**The test for a deep module:**
Can you describe what this module does in one sentence?
Can an agent working in a different module use this
one without knowing its internals?
If yes — the module is deep enough.
If no — redesign before building further.

**Interface design comes before implementation.**
Design the boundary first.
What does this module expose?
What does it hide?
Once the interface is settled, implementation
can be safely delegated to an agent.

## 07 — The vertical slice standard

Features are built as vertical slices —
thin cuts through the entire stack that deliver
something testable end to end.

Not horizontal layers.
Not "build all the database models first, then the API,
then the UI." One slice at a time, always working
end to end, always deployable.

**The vertical slice sequence:**
Schema change → API endpoint → UI surface → Test.
All four in one slice. All four before the next slice begins.

This is what makes agent-assisted development trustworthy —
each slice is verifiable before the next begins.
The agent cannot outrun the tests.
