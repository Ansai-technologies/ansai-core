# ADR-001 — Multi-Tenant Shared Schema Architecture
Date: May 2026
Status: Active
Decided by: Amasai Melchizedek

---

## Decision

EduManage uses a shared PostgreSQL schema with school_id
as a foreign key on every table that contains
institutional data, enforced at middleware level
through tenantGuard in @ansai/tenancy.

Every query that touches institutional data must include
WHERE school_id = ? or the Prisma equivalent.
This is enforced structurally — not by convention.

---

## Reason

Three alternatives were considered:

**Option A — Separate database per school.**
Each school gets its own PostgreSQL database.
Complete isolation at the database level.
Rejected because: at 10 schools this is manageable.
At 100 schools, connection pooling becomes a serious
engineering problem. At 500 schools, running migrations
across N databases simultaneously is operationally
unacceptable for a small team.
The operational cost compounds with every school added.

**Option B — Separate schema per school.**
Each school gets its own PostgreSQL schema within
one database. Moderate isolation.
Rejected because: same migration problem as Option A,
plus schema proliferation creates its own complexity.
Still operationally expensive at scale.

**Option C — Shared schema with school_id scoping.**
One database. One schema. Every institutional table
has school_id. Isolation enforced at middleware level.
Chosen because: migrations run once. Connection pooling
is trivial. Operational complexity is constant regardless
of the number of schools. The isolation guarantee is
as strong as the middleware — which is why the middleware
must be non-bypassable.

The decision trades database-level isolation for
operational simplicity. The security guarantee is
maintained through code — not through database architecture.
This requires absolute discipline on tenant scoping.
That discipline is enforced by tenantGuard in @ansai/tenancy.

---

## Consequences

**What this means for all engineers and agents:**

Every query touching institutional data must be scoped.
The tenantGuard middleware is non-bypassable.
A query without school_id scoping is a gross violation —
see ansai-core/AGENTS.md Section 04.

Every new table that contains institutional data must
have school_id as a non-nullable foreign key.
This is checked in code review on every pull request.

The @ansai/tenancy primitive enforces this.
Never implement tenant scoping manually in application
code — always use the primitive.

**What this means for Ansai Core:**

The @ansai/tenancy package is the most critical
primitive in the entire ecosystem.
Changes to it affect every product line simultaneously.
Changes require Category 3 amendment governance.

**What this means at scale:**

This decision remains correct up to approximately
10,000 schools in a single database instance.
Beyond that, horizontal sharding becomes necessary.
That decision will be revisited as an amendment
to this ADR when that scale is approached.
Until then — this decision is final.
